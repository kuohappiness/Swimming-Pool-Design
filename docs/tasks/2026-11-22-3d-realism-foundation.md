## 目的

3D 頁現況在電腦高畫質下一個畫面要 2,029 次繪製呼叫、46 支著色器，水面與兩種玻璃各把整個場景重畫一次，貼圖是不到 1 KB 的代理圖樣。直接往上加寫實效果只會更卡。

階段一先把地基打好，之後的水（階段二）與光（階段三）才有地方放：

- 把「流暢度不可犧牲」寫成機制：畫質分四級、啟動時自動選級、幀率掉到底線以下就先降解析度再關效果，有餘裕再恢復。
- 把成本寫成數字並由自動檢查擋住：每一級的繪製呼叫、三角形、下載量，以及入庫資產的容量。
- 建立寫實貼圖的管線：壓縮貼圖（KTX2）、來源與授權登錄、烘焙光照圖。

不做的話，寫實效果只能靠事後實機抱怨來收，沒有任何一條自動檢查會在變慢時提醒。

## 與現行慣例不同、需要使用者同意的兩點

這兩點偏離已核准的資料夾慣例，使用者同意前不新增這兩類檔案（B、D 才會用到）：

1. **第三方原始貼圖不入庫，只入庫轉檔後的 `.ktx2`。** 現行慣例是原始來源只增不改、全部保存。寫實貼圖的原始檔一組約 50～200 MB，全部入庫會讓 repo 膨脹到數 GB。改為在資產清單記下原始檔網址、作者、授權、SHA-256 與轉檔設定，任何人都能重新下載並轉出相同的檔。自製的原始檔仍照慣例放 `source-materials/` 並給來源編號。
2. **烘焙光照圖是產生檔，但入庫。** 現行慣例是產生檔不入庫。光照圖烘焙一次要數分鐘並需要完整模型，放在每次建置裡會拖慢所有 PR 的檢查。改為入庫，並由登錄檔記下模型雜湊與烘焙設定；模型幾何變了沒重烘焙時檢查直接失敗，並印出要跑的指令。

## 驗收

A 部分：

- 四級畫質由高到低成本只降不升，上限數字只寫在 `core/viewer/render-budgets.mjs` 一處。
- 幀率調節器：短暫卡頓不動作；持續低於底線時先降解析度到 70%，再依固定順序關效果；持續 10 秒有餘裕才恢復一步；恢復後立刻又掉幀時，下次恢復的等待時間加倍；分頁切到背景不計時。
- 啟動選級順序：網址 `quality` 參數、使用者手動選過的、軟體繪圖一律省電、啟動檢測、保守預設；手機自動選級最高到「中」。
- `npm run check:assets` 擋下超過單檔上限、超過資料夾總量、未登錄副檔名與不合命名規則的資產，並納入 `npm run build` 與 CI。

整個階段一完成時：

- 固定鏡位的 e2e 斷言：繪製呼叫電腦極致級 500 以內、手機中級 200 以內；三角形 80 萬與 25 萬以內；每個畫面的貼圖重新上傳次數為 0。
- 各級下載量：省電 4 MB、中 8 MB、高 20 MB、極致 40 MB 以內。
- 真實幀率由使用者在實機回報：雲端檢查環境沒有顯示卡，量不到真實幀率，所以幀時間只做診斷、不做自動斷言。

## 結果

A 部分（2026-11-22）：新增 `core/viewer/render-budgets.mjs`、`web/src/views/3d-viewer/rendering/performance/`（`realism-tiers`、`tier-selection`、`frame-governor`）與 `tools/check/check-assets.mjs`，單元測試 26 項。這一部分沒有改動畫面，3D 頁仍使用現行三級畫質。

B 部分（2026-11-22）：資產清單改為單一 JSON（`web/src/views/3d-viewer/assets/asset-manifest.json`），新增 `npm run build:textures`（`tools/build/build-textures.mjs` 與 `tools/build/textures/`）與 KTX2 載入器（`rendering/textures/ktx2-texture-source.ts`）。第一張貼圖是自製的水面細波紋法線貼圖，512 × 512、301 KB。

- 編碼器用開發用套件 `ktx2-encoder`（WebAssembly），不需要另外安裝命令列工具，Windows、macOS、Linux 都能跑同一個指令；同樣的輸入連轉兩次，輸出逐位元組相同。
- 用無顯示卡的 Chromium 實際載入驗證，開發伺服器與正式打包各一次：貼圖轉成 BC7 壓縮格式、10 層縮圖、線性色彩空間，繪製後讀回像素正確，沒有 WebGL 錯誤。
- 轉碼器隨網站打包後是一支 58 KB 的腳本加一個 527 KB 的 WASM，只在用到 KTX2 貼圖時下載；接上畫面時這 0.6 MB 要算進各級的下載量。
- 這一部分仍然沒有改動畫面：新貼圖與載入器尚未被 3D 頁使用。
- 範圍內還沒做的：第三方來源的貼圖需要清單再加原始檔網址與雜湊欄位，等使用者同意上面第 1 點後一起做。

C 部分前半（2026-11-22，與 [TASK-151](2026-11-22-3d-realism-water.md) 同一個 PR）：水不再用 transmission 重畫場景，KTX2 貼圖第一次真的用在畫面上；e2e 的繪製呼叫與三角形上限改讀 `core/viewer/render-budgets.mjs`，手機中級由 250 收緊到 200（實測 168）。電腦中級目前 261 次，仍高於中級的 200，差的就是玻璃的 transmission 那一次重畫，後半處理完再把電腦中級加進 e2e 斷言。

C 部分後半之一（2026-11-22，同一個 PR）：玻璃與濕地面水膜不再用 transmission。

- 新增 `rendering/enhanced/glossy-film-material.ts`：一次混合就算完的薄膜材質，「畫面＝倒影＋霧面色 × 不透明度＋背景 ×（1 − 不透明度）×（1 − 菲涅耳反射率）」。倒影不被不透明度打折，所以正看幾乎透明、斜看倒影變強。屋頂玻璃、安全玻璃與濕地面三種材質共用同一支著色器。
- 載入前與載入失敗時的舊水面也拿掉 transmission，enhanced rendering 任何一級都不會再觸發那一次整場景重畫，也不會配置那張全畫面的暫存畫布。單元測試逐一檢查三級畫質的每一種語意材質。
- 繪製呼叫實測（無顯示卡 Chromium，預設鏡位）：電腦高級 294 → 163、電腦中級 261 → 145、手機中級 168 → 97、低級 83 → 76；三角形電腦高級 109,930 → 55,258。電腦中級已加進 e2e 斷言（上限 200）。
- 低畫質沒有環境貼圖，拿不到倒影的顏色，玻璃退回較濃的半透明色片，外觀與改前接近。
- `?rendering=baseline` 的診斷用基準材質維持原樣（安全玻璃 transmission 0.16 是契約測試固定的值），不在這次範圍。
- 已知限制：倒影取自整個場景共用的環境貼圖（天空），從室內看玻璃內側照到的也是天空而不是室內；濕地面先用倒影強度 0.4 近似天花板。區域倒影留到階段三（光與天空）一起做。
