## 目的

3D 頁每幀要畫兩千多次，手機與一般筆電吃不消，也讓 3D 串接下來的寫實渲染沒有預算空間。不做的話，每多加一件陳設就多一次繪製。合併後繪製次數只跟「材質數 × 切換單位數」有關，新增的幾何自動併進去。

## 範圍

| 問題 | 修法 |
| --- | --- |
| 768 個網格各自一次繪製，每個網格再掛一條邊線 | 新增 `web/src/views/3d-viewer/scene-batcher.ts`，在視覺細節掛上前依（切換單位、材質、陰影設定、類別）合併網格與線條；768 個網格併成 134 個 |
| 合併後點選會找不到構件 | 每個三角形記錄所屬構件（`faceOwners`），點選改對整個場景做射線再依三角形找構件；選取框用合併前的範圍 |
| 3D 寫實渲染需要分組（倒影排除水面、陳設等） | 每個網格保留圖層 0，另加九個類別之一的圖層，類別可由 `userData.renderCategory` 指定 |
| 水面法線貼圖每幀 `needsUpdate`，整張貼圖每幀重傳 | 只在改變重複方式時上傳一次，捲動只改 offset |
| 漫遊時每幀呼叫水面 `apply()`，材質每幀重編譯 | 移動模式或剖視狀態真的改變才重設材質 |
| 3D 串的畫質調節器需要分開的幀間隔與工作時間 | 新增 `frame-statistics.ts`，公開最近 120 幀的間隔 p95 與 CPU 工作時間 p95（GPU 計時之後再加） |

不在範圍：玻璃與水面的透射 pass（約占剩下繪製的一半，屬 3D 串的 rendering，3D 階段一處理）；實例化繪製（目前重複構件已在合併中處理，3D 串加入大量陳設與人物時再評估）。

## 驗收

量測（雲端 SwiftShader，`adaptive=off`，三角形數合併前後相同）：

| 畫質與視窗 | 合併前繪製次數 | 合併後 |
| --- | --- | --- |
| 桌機 high | 2,029 | 373 |
| 桌機 medium | 1,898 | 330 |
| 桌機 low | 619 | 84 |
| 手機 medium | 1,122 | 237 |

手機三角形數由 59,160 增為 84,860，因為合併後的網格範圍較大、視錐裁切較少，仍遠低於 25 萬上限。

新增 `tests/unit/web/views/3d-viewer/scene-batcher.test.mjs`：合併前後每個三角形的世界座標、繞向、所屬構件、圖層、剖視物件與細節等級逐一相同（故意把所屬構件寫錯時測試會失敗）；網格數至少減為四分之一；水面、地坪、焦散與剖視物件保持原物件；每個構件仍可被點選且選取範圍不變；鏡像變換不翻面；合併不跨圖層、材質與細節等級；類別推得與報錯；每個網格的圖層遮罩。另新增 `frame-statistics.test.mjs`（間隔與工作時間分開、視窗只留最近的幀）。e2e 新增桌機 high 與手機 medium 的繪製次數、三角形與合併比例硬上限。`npm run lint`、`npm run build`、`npm run test:e2e` 通過。
